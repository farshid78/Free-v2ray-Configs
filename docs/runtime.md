# معماری اجرا، زمان‌بندی و وضعیت پایدار

این سند بر پایهٔ **اندازه‌گیری واقعی** نوشته شده است، نه فرض. هر عددی که این‌جا
آمده از API اجراهای همین مخزن یا از اجرای واقعیِ همین کد روی سیستم گرفته شده.

## ۱. زیرساخت واقعی

| بخش | کجا اجرا می‌شود | محدودیت‌ها |
|---|---|---|
| ربات تلگرام | ماشین همیشه‌روشنِ مالک (یا برش‌های GitHub Actions) | long-polling؛ یک نمونه با یک توکن؛ ~۲۰ پیام در دقیقه برای هر کانال |
| تجمیع/اعتبارسنجی | GitHub Actions (`ubuntu-latest`) | سقف ۶ ساعت برای هر job، cron با تأخیر، خاموشیِ زمان‌بندی پس از ۶۰ روز بی‌فعالیتی |
| خروجی داده | شاخهٔ `main` + GitHub Pages + raw/jsDelivr | force-push تک‌کامیتی، کشِ لبهٔ CDN |
| وضعیت/صف | شاخهٔ `state` + SQLite محلی | جدا از `main` تا force-push پاکش نکند |

مخزن عمومی است، پس دقیقهٔ Actions محدودیت ندارد؛ برای مخزن خصوصی همین چیدمان
(~۱۸۰۰ دقیقه در روز برای ربات) از سهمیهٔ ماهانه بیشتر است.

### اندازه‌گیریِ ۲۵ اجرای اخیر (API گیت‌هاب)

| نوع اجرا | مدت | توضیح |
|---|---|---|
| اجرای کاملِ تجمیع | ۶۱۰، ۶۱۱، ۶۱۵، ۶۴۳، ۶۵۷، ۶۶۱، ۶۷۴، ۶۹۸، ۷۱۷ ثانیه | میانه ≈ ۶۵۷ ثانیه (۱۱ دقیقه) |
| اجرای ردشده با دروازهٔ تازگی | ۴۰ و ۷۴ ثانیه | فقط checkout + gate |
| `startup_failure` | ۲ مورد، ۱ ثانیه | خطای پیش از اجرای گام‌ها |
| `cancelled` | ۱ مورد، ۴۰ ثانیه | اجرای جایگزین‌شده |

نتیجه‌های عملی:

- بودجهٔ ۲۰ دقیقه‌ای job با میانهٔ ۱۱ دقیقه **۱.۸ برابر** حاشیه دارد.
- تأخیر صف در گزارش API صفر دیده می‌شود، ولی این عدد قابل اتکا نیست
  (`run_started_at` تقریباً همیشه برابر `created_at` است). تأخیر واقعیِ صف از
  `started_at` هر job می‌آید و در همین مخزن تا چند دقیقه دیده شده.
- دو `startup_failure` نشان می‌دهد «سبز بودنِ آخرین اجرا» شاخص خوبی برای
  سلامتِ سیستم نیست — دقیقاً همان دلیلی که `status.json` ساخته شد.

## ۲. معماری: دو بخشِ مستقل

```
┌──────────────────────────────┐        ┌────────────────────────────────┐
│  سرویس دائمی ربات            │        │  Workflowهای زمان‌بندی‌شده      │
│  bot/main.py                 │        │  aggregate.yml                 │
│  • poll + منو + پنل ادمین    │        │  • health → collect → dedup    │
│  • heartbeat هر ۶۰ ثانیه     │        │  • cascade (L0→L3) + google    │
│  • صفِ ارسال (outbox.sqlite) │        │  • validate → publish          │
└──────────────┬───────────────┘        └───────────────┬────────────────┘
               │ هر ۵ دقیقه                             │ پایانِ هر چرخه
               ▼                                        ▼
        ┌─────────────────────────────────────────────────────┐
        │  شاخهٔ state  →  status.json (وضعیت، شمارنده، تاریخچه)│
        └─────────────────────────────────────────────────────┘
                               │
                               ▼
                    docs/miniapp.html (بخشِ «وضعیت سیستم»)
```

چرا دو بخش: ربات به **فرایندِ زنده** نیاز دارد و Actions فرایندِ دائمی نمی‌دهد؛
تجمیع به **داده و شبکه** نیاز دارد و روی ماشینِ خانگی غیرقابل‌اتکاست. هیچ‌کدام
جای دیگری را تقلید نمی‌کند.

### ۲.۱ سرویسِ ربات

- `bot/main.py` با `BOT_RUN_MINUTES` عمر می‌گیرد (۰ = بی‌نهایت، حالت سرویس).
- `heartbeat_job` هر ۶۰ ثانیه زمانِ زنده را در `data/runtime/status.json` می‌نویسد؛
  `status_publish_job` هر ۵ دقیقه آن را روی شاخهٔ `state` منتشر می‌کند.
- در `finally` وضعیت به «آفلاین» تغییر می‌کند، پس داشبورد هرگز «آنلاینِ کهنه»
  نشان نمی‌دهد.
- اگر نمونهٔ دیگری با همان توکن poll کند، پیش از شروع با یک `getUpdates`
  تشخیص داده می‌شود و این نمونه در چند ثانیه کنار می‌رود (نه ۲۵ دقیقه آویزان).

### ۲.۲ Workflowهای زمان‌بندی‌شده

| Workflow | cron | دروازه | کار |
|---|---|---|---|
| `aggregate.yml` | `*/5 * * * *` | تازگیِ ۱۳ دقیقه | چرخهٔ کاملِ داده + انتشار روی `main` |
| `live.yml` (اختیاری/پشتیبان) | `*/20 * * * *` | — | برشِ ۲۵ دقیقه‌ای ربات |

محاسبهٔ فاصله‌ها:

- **تجمیع**: هر ۵ دقیقه یک تیک، ولی اگر `index.json` کمتر از ۱۳ دقیقه قدم
  داشته باشد چرخه کارِ سنگین نمی‌کند ⇒ به‌روزرسانیِ مؤثر ~۱۵ دقیقه، با این
  مزیت که یک تیکِ ازدست‌رفته با تیکِ بعدی (۵ دقیقه بعد) جبران می‌شود. با
  میانهٔ ۱۱ دقیقه اجرا، حداکثر ~۷۳٪ زمان اشغال است و ۲۷٪ حاشیه می‌ماند.
- **ربات**: هر برش ۲۵ دقیقه زنده است و هر ۲۰ دقیقه یکی ساخته می‌شود ⇒ همیشه
  یک برشِ صف‌شده وجود دارد. اگر برشِ فعلی بمیرد، صف فوراً جای آن را می‌گیرد.
- **ارسال به کانال**: فاصلهٔ تصادفی ~۳.۳ ثانیه ⇒ ~۱۸ پیام در دقیقه. اندازه‌گیری:
  ۴۰ و ۲۵ پیام در دقیقه هر دو `Flood control` دادند؛ ۱۸ در دقیقه بدون خطا.

## ۳. قفل، مالکیت و بازیابی

| موقعیت | رفتار |
|---|---|
| دو چرخهٔ هم‌زمان | `scripts/status.py begin` قفل با `owner` + `expires_at` می‌گیرد؛ دومی کد ۷۵ می‌گیرد و گام‌های سنگینش skip می‌شوند |
| اجرای کشته‌شده | قفل پس از TTL (۴۰ دقیقه) خودبه‌خود آزاد می‌شود؛ نیازی به دخالت دستی نیست |
| وضعیتِ خراب | `load()` فایلِ ناخوانا را «پیش‌فرض» می‌خواند (fail-open) و چرخه ادامه می‌یابد |
| شکستِ یک مرحله | مراحل اختیاری (`cascade`, `google`) از قبل `continue-on-error` دارند؛ گزارشِ پایان با `if: always()` همیشه ثبت می‌شود |
| خطای ارسال به کانال | پیام در SQLite می‌ماند، `attempts++`، backoff نمایی (۵s → ۳۰۰s، حداکثر ۲۰ تلاش) |
| جریمهٔ تلگرام | دورِ جاری متوقف می‌شود، بقیهٔ صف دست‌نخورده می‌ماند و فاصله بزرگ‌تر می‌شود |
| ری‌استارت/برشِ تازه | صف و دفترِ idempotency روی دیسک‌اند؛ هیچ حالتِ درون‌حافظه‌ای لازم نیست |

### Idempotency

کلیدِ هر کانفیگ = `sha256(بخشِ اتصال، بدونِ remark)[:16]`. پیش از ارسال، وجودِ
کلید در `ledger` بررسی می‌شود؛ پس یک کانفیگ با هیچ ترتیب/برش/ری‌استارتی دو بار
به کانال نمی‌رود. مهاجرت از سامانهٔ قدیمی (offset) با پرکردن دفتر برای ۴۴۳
کانفیگِ قبلاً ارسال‌شده انجام شد تا گذار، ارسالِ تکراری نسازد.

⚠️ حدِ صادقانه: اگر پروسه **بینِ** پاسخِ موفقِ تلگرام و نوشتنِ `mark_sent` کشته
شود، آن یک پیام در اجرای بعد دوباره می‌رود. Telegram برای `sendMessage` کلیدِ
idempotency ندارد؛ این پنجره به چند میلی‌ثانیه محدود شده ولی صفر نیست.

## ۴. چرخهٔ کاملِ پردازش (ترتیبِ واقعی در `aggregate.yml`)

1. `🌍` سلامتِ منابع و GeoIP (health.json هر منبع)
2. `🚀 Run aggregator` → واکشی، dedup، برندینگ (`index.json`, `all/`, `heavy/`, `light/`)
3. `🔀 cascade` → L0→L3 روی `all/configs.txt` → `verified/ fast/ secure/ top100.txt`
4. `🟢 google` → آزمونِ واقعیِ سرویس‌های گوگل روی `verified/`
5. `🔍 validate` → اعتبارسنجی با کلاینت‌های واقعی (strict)
6. `🚀 Publish` → rolling squash روی `main` + purge کش
7. ربات از `verified/` صف می‌سازد و به کانال می‌فرستد (بیرون از workflow، در سرویس)
8. داشبوردها `index.json` و `status.json` را زنده می‌خوانند
9. `🧾 Report cycle` → ثبتِ مراحل، شمارنده‌ها، تاریخچه و انتشار روی `state`

## ۵. پایش (بخشِ «وضعیت سیستم» در پنل گلس)

`docs/miniapp.html` → تبِ «خلاصه» → کارتِ وضعیت، این‌ها را از `status.json`
می‌خواند:

- ربات: آنلاین/آفلاین + سنِ heartbeat (آستانهٔ آفلاین: ۳۰۰ ثانیه)
- آخرین چرخه: موفق/ناموفق، مدت، خطا
- آخرین استخراج + تعداد کانفیگ‌های خوانده‌شده
- معتبر / نامعتبر / تکراری / جدید
- ارسال: موفق، تلاشِ ناموفق، در صف
- وضعیت هر workflow + مراحلِ همان چرخه
- هشدارِ کهنگی اگر `status.json` بیش از ۲۰ دقیقه به‌روز نشده باشد

## ۶. محدودیت‌های باقی‌مانده

1. **دقتِ cron**: تریگرِ Actions می‌تواند چند دقیقه تأخیر کند؛ هم‌پوشانیِ ۵
   دقیقه‌ای برش‌ها آن را جبران می‌کند، ولی «تضمینِ صفرِ وقفه» فقط با VPS ممکن است.
2. **سقف ۶ ساعت و خاموشیِ ۶۰ روزه** برای workflowهای زمان‌بندی‌شده.
3. **پنجرهٔ idempotency** بالا (چند میلی‌ثانیه).
4. **کشِ لبهٔ CDN**: `raw` چند دقیقه کش می‌کند؛ داشبورد برای وضعیت از
   cache-buster استفاده می‌کند، برای `index.json` نه.
5. **وابستگیِ وضعیت به git**: اگر push به شاخهٔ `state` شکست بخورد، وضعیت
   محلی درست است ولی داشبورد کهنه می‌ماند (fail-open، بدون توقفِ چرخه).

میزان اطمینان: مکانیزم‌های قفل/صف/backoff/heartbeat با ۱۲ تست واحد و چند اجرای
واقعی سنجیده شده‌اند. اجرای واقعیِ `aggregate.yml` با این تغییرات روی گیت‌هاب
هنوز دیده نشده (نیازمند push و اجرای بعدی) و `live.yml` بدون Secretِ `BOT_TOKEN`
آزمون‌پذیر نیست.
